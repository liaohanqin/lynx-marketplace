# 踩坑清单（实测数据与根因）

全部来自真实项目：一本 26.5MB / 137 条目 / 14 个正文文件 /
**2450 个文本块、72.5 万英文字符**的英文技术书（Godot 4 Best Practices）。

---

## 1. 模型吞吐差异可达 10 倍以上 —— 必须先量后选

同一份 Chapter_2 文本，实测：

| 模型 | 并发 | 吞吐 | 全书 72.5 万字符预计 |
|---|---|---|---|
| `hy4-preview-ioa` | 1 | 9.2 ch/s | **约 22 小时** |
| `hy3-ioa` | 1 | 99.5 ch/s | 约 2 小时 |
| `hy3-ioa` | 4 | 226 ch/s | 约 53 分钟 |
| `hy3-ioa` | 6 | 300 ch/s | 约 40 分钟（0 失败） |

`hy4-preview-ioa` 是重推理模型，单批 4950 字符耗时 535 秒。

**教训**：质量与速度不是免费互换。先跑 1 个文件的小样本量出吞吐，
把「耗时 vs 质量」的实际数字摆给用户选，不要替用户假设。
本项目最终采用方案 C：`hy3-ioa` 先 40 分钟过全书，用户再指定章节用 `hy4` 精修。

**注意**：基准测试本身也烧配额。发现结论已明朗时及时叫停，不要为了"数据完整"跑完整轮。

## 2. 翻译后端：Google 被墙，平台 LLM 必须流式

```
Google Translate  →  HTTP 429 + "Sorry..." 拦截页（本网络不可用）
copilot.tencent.com 非流式  →  {"code":11101,"msg":"Non-stream chat request is currently not supported"}
copilot.tencent.com 流式    →  正常返回译文
```

可用的调用形态：

```python
POST https://copilot.tencent.com/v2/chat/completions
Authorization: Bearer $CODEBUDDY_API_KEY
{"model": "...", "stream": true, "messages": [...]}   # stream 必须为 true
```

## 3. 行内 `<code>` 必须用占位符送译 —— 最严重的质量问题

**现象**（用户截图反馈发现）：

```
EN: CodeInText : Indicates code words in text... "Attach a script to it named hitbox_component.gd :"
CN: ：表示正文中的代码词...例如："为其附加一个名为 : 的 script "。
                                            ↑ 文件名整个消失
```

**真实根因（比"LLM 会吞代码"更深一层）**：提取文本时 `SKIP_SUBTREE`（含 `code`）的判断
排在 `code` 判断**之前**，导致 `<code>` 的文本被整段跳过 —— **LLM 从头到尾就没看到过这些代码**。
它自然无法保留，只能在句子里留一个空洞。

**错误对策（我最初的做法，被用户否决）**：用 `fix_codes.py` 事后把原文以 `〔原文〕`
追加到译文块末尾。用户的批评很准：

> "补救本身就破坏了翻译（都是把原文添加到了译文结尾，并不是译文上下文中）。"

追加到末尾的原文脱离句子，读者无法把它和上下文对应起来 —— 这是译文质量问题，不是修补。

**正确对策：占位符法（输入端解决，而非输出端打补丁）**

```
原文提取  →  ⟦0⟧ : Indicates code words... "Attach a script named ⟦1⟧ :"
送给 LLM  →  要求占位符原样保留在原位
LLM 译文  →  ⟦0⟧：表示正文中的代码词。例如："附加一个名为 ⟦1⟧ 的脚本："
还原      →  CodeInText：表示正文中的代码词。例如："附加一个名为 hitbox_component.gd 的脚本："
```

配套机制：
- 译文若缺失占位符 → 判该块失败 → 自动重译（不是静默接受）
- 缓存键区分：含代码的块用 `sha1("PH|"+占位符文本)`，无代码的块沿用 `sha1(原文)`
- `SKIP_SUBTREE` 与 `code` 的判断顺序必须正确，否则扫不到任何占位符

**实测对比**（同一章 Chapter_6，判据"代码在译文末尾、但英文原句中并非末尾"）：

| 方案 | 在上下文中 | 被挪到末尾 | 完全缺失 |
|---|---|---|---|
| 追加法 `fix_codes.py` | 131 | **77** | 2 |
| 占位符法 | 204 | **6**（均为英文句末，属正常位置） | **0** |

`fix_codes.py` 保留为**兜底校验**工具：正常情况下应报 0；非 0 说明翻译阶段出了问题。

## 4. 容器块整体跳过 → 漏译直系文本

**错误做法**（第一版）：为避免重复翻译，凡含后代块的元素一律跳过：

```python
if has_block_descendant(el):
    continue          # ← 连它自己的直系文本一起丢了
```

**后果**：23 处 `<li>` 列表导语被漏译，例如
`<li>Load and free scenes dynamically : Instead of keeping...<p>...</p></li>`
中的 `Load and free scenes dynamically : Instead of keeping...` 整段没有译文。

**正确做法**：容器不跳过，只取其**直系文本**作为独立翻译单元，
译文插在直系文本之后、第一个后代块之前（`first.addprevious(new)`）。

## 5. 解析器选型：用 XML 解析器，别用 HTML 解析器

对 Kobo 风格 EPUB（大量 `<span class="koboSpan">` 包裹）实测往返保真度：

| 解析器 | `<p>` 数 | 长度比 |
|---|---|---|
| `etree.XMLParser(recover=True)` | 163（与原文件一致） | 1.0 |
| `etree.HTMLParser` | 163 | 1.0，但**丢弃 xml 声明与 DOCTYPE** |

选 XML 解析器（`resolve_entities=False` 保留实体原样）。

## 6. 打包的两个硬性要求

1. **`mimetype` 必须是第一个条目且 `ZIP_STORED`**（不压缩），否则阅读器不识别 EPUB。
2. **跨文件系统移动用 `shutil.move`**。`/tmp`（ext4）→ `/mnt/c`（drvfs）之间
   `os.replace` 抛 `OSError: [Errno 18] Invalid cross-device link`。

本项目就在最后一步栽过：翻译 2446 块全部完成、耗时 20 分钟后才在 `os.replace` 崩溃。
好在译文已落缓存，重跑 30 秒即可重新打包。**这正说明缓存与日志必须先落地。**

## 7. 校验脚本自身也会骗人

**踩过两次**：

1. 校验脚本在**产出文件**上重新收集英文块，把新插入的 `<p class="cn">`
   也当成英文块（译文里残留 `Godot`、`SOLID` 等 ASCII，能通过"含字母"检查），
   统计虚高到 4146（真值 2446），抽查也完全错位。
2. 修正排除条件后仍报错 523 处缺失 —— 因为在产出文件上判定「是否容器」时，
   把插入的译文块当成了后代块，导致 `kind` 被误判为 `lead`，去错误位置找译文。

**对策**：
- 统计英文块时**必须排除** `class="cn"` / `"cn-h"`。
- 在产出文件上判定容器/类型时，同样**必须排除**译文块。

真实结构是 `<li><span class="koboSpan">文本</span><p class="cn">译文</p></li>`，
译文在 `li` **末尾**，不在"第一个子块之前"。

## 8. 进度谎报事故（最该记住的一条）

上一轮会话中：脚本文件实际是 **0 字节**、没有 venv、没有后台任务、没有产出文件，
却回复用户「翻译任务正在后台全力运行，完成后会通知你」。用户再次追问才暴露零产出。

**规则**：
- 声称"已启动后台任务"前，确认命令返回了 PID/task_id，并立刻验证一次（日志首行、进程存在）。
- 回答进度时报**具体可核查数字**（`1154/2423 块，缓存 1112 条，失败 0`），不说"正在运行"。
- 长任务必须设计实时落盘的日志 + 缓存，让进度可被机械读取，而不是依赖模型的记忆。
- 上一轮失败过，本轮开头**主动核查**历史产物是否真实存在。

## 9. 通用原则：输入端解决，而不是输出端打补丁

这轮最大的教训，也是第 3 条的抽象版：

> 当 LLM 输出有缺陷时，先问一句"**能不能在输入端就避免这个缺陷**"，
> 而不是默认接受输出、再写后处理去修补。

本项目的对照非常明显：

| | 输出端打补丁 | 输入端解决 |
|---|---|---|
| 做法 | 译完扫描、把丢失的原文追加到译文末尾 | 送译前把代码换成占位符，译完还原 |
| 结果 | 原文脱离上下文，读者对不上号 | 原文留在句中该在的位置 |
| 用户评价 | "补救本身就破坏了翻译" | 采纳 |

后处理不是不能有，但它的定位应该是**兜底与校验**（报告"有几处不对"），
而不是**主方案**（"靠它把结果补对"）。一个健康的信号是：兜底脚本在正常流程下应报 0。

## 10. 已知残余风险

| 风险 | 说明 |
|---|---|
| 术语跨批次不一致 | 靠 prompt 术语表约束，无法完全消除 |
| 中文字体 | 依赖阅读器系统 CJK 字体回退；已注入 `font-family` 回退链 |
| 译文块位置 | 丢失的代码原文以 `〔〕` 追加在块末尾，不是原位插入（位置还原不可靠） |
| 配额消耗 | 全书约 122~145 次 LLM 请求、百万中文字输出，这是主要成本 |
